# 调用 A* 路径规划服务

规划服务只做规划，不控制机器狗：输入“当前位置 + 一串目标”，输出每一段避开障碍的折线。
要让仿真中的机器狗沿路线走，接着用 `mujoco-path-following` 技能；完整的“说一句话就走过去”流程见 `go2-mujoco-navigation` 技能。

本技能可以在局域网内任何一台电脑上使用，只需要 `curl`。

## 服务器地址

| 服务 | 地址 |
|---|---|
| A* 规划服务（本技能） | `http://192.168.104.191:8765`（HTTP）；`ws://192.168.104.191:8766`（WebSocket，功能相同） |
| 仿真控制服务（`mujoco-path-following` 用） | `http://192.168.104.191:8770` |

两个服务运行在同一台电脑上。用户告诉你服务器 IP 变了，或环境变量 `ROBOT_HOST` 已设置时，以它为准：

```bash
H=${ROBOT_HOST:-192.168.104.191}
A=http://$H:8765
```

- curl 一律加 `--noproxy '*'`：很多电脑设置了系统代理，不加会把局域网请求发到代理上，表现为超时或 502。
- Windows 上用 `curl.exe`（PowerShell 里的 `curl` 是另一个命令的别名）；JSON 请求体放进文件再用 `--data-binary @文件` 发送，可以避开引号转义问题。

## 第一步：确认服务在线

```bash
curl -s --noproxy '*' $A/health
# {"ok": true, "map_id": "go2_room_selfbuilt", "map_version": "2026-11-09.2", "waypoints": 3, "scene_graph": false}
```

- 连不上（超时、拒绝连接）：先 `ping` 服务器；能 ping 通但端口不通，说明服务没运行或被防火墙挡住。
  这需要有人在服务器上处理（见文末“服务器端维护”），告诉用户，不要反复重试。
- 记下 `map_id` 和 `map_version`：要和仿真控制服务的地图一致（`mujoco-path-following` 会核对）。

## 第二步：把用户的话翻译成规划请求

规划请求有三样东西：起点 `start`、有序目标列表 `goals`、可选的加密间距 `step`。

### 目标

先查点位表，了解当前地图有哪些地方：

```bash
curl -s --noproxy '*' $A/waypoints          # 每个点位的编号 id、名称 name、语义标签 semantic_tags、站位 stand_pose
curl -s --noproxy '*' $A/scene_graph        # 只有 health 中 scene_graph 为 true 的地图才有：物体和区域
```

`goals` 的每一项可以是**名称字符串**，也可以是**坐标对象**，两种可以混在一个列表里：

| 用户的说法 | 写进 `goals` 的项 | 说明 |
|---|---|---|
| 点位名称：“去广告牌” | `"广告牌"` | 最可靠 |
| 点位编号：“去 wp_02” | `"wp_02"` | 不区分大小写 |
| 语义标签或名称的一部分：“去厕所” | `"restroom"` 或 `"厕所"` | 服务按 编号 → 名称全等 → 语义标签 → 名称包含 的顺序匹配 |
| 回出发点：“回去充电”“回充电桩”“回原点” | `"wp_00"` | 充电桩是地图原点 |
| 场景图物体：“去标定板”“去东侧通道里的手推车” | `"标定板"`、`"东侧通道里的手推车"`、`"obj_17"` | 同名物体有多个时必须带区域名或编号 |
| 坐标：“走到 (2, 3)” | `{"x": 2, "y": 3}` | |
| 坐标并指定朝向：“走到 (2,3) 面朝 +y” | `{"x": 2, "y": 3, "yaw": 1.5708}` | 弧度，+x 为 0，逆时针为正 |
| 相对移动：“往前走 2 米”“向左 1 米” | 换算后的坐标对象 | 先读当前位姿 `(x, y, yaw)`：前方 d 米为 `(x + d·cos yaw, y + d·sin yaw)`，左方 d 米为 `(x − d·sin yaw, y + d·cos yaw)`，后、右取负 |
| 多个目标有先后：“先去厕所通道再去广告牌” | `["厕所通道", "广告牌"]` | 列表顺序就是行走顺序，可以重复 |
| 去了再回来：“去广告牌再回来” | `["广告牌", "wp_00"]` 或回到出发坐标 | “回来”要显式写成终点 |
| 巡视所有点位 | 除充电桩外所有点位按编号排序，最后加 `"wp_00"` | |

需要你自己做的语义理解：

- 用户的说法和点位名称不完全一样时（“去看看那块广告”“去洗手间那边”），对照点位表的名称和语义标签选出对应点位，用它的**编号**发请求，并在回复里说明你理解成了哪个点位。
- 对得上多个点位、或一个都对不上时，不要猜：把可选点位列给用户，请用户选。
- 用户没说“回来”，就不要自动加返回充电桩。

### 起点

| 情况 | 起点 |
|---|---|
| 要让仿真中的机器狗接着走 | **必须**用仿真器中的实际位置：`curl -s --noproxy '*' http://$H:8770/pose`（返回的 JSON 可以直接作为 `start`，多余字段会被忽略） |
| 仿真器刚启动、机器狗还没动过 | `{"x": 0, "y": 0, "yaw": 0}`（地图原点） |
| 用户明确给出起点 | 用户给的值 |
| 只是“看看从 A 到 B 怎么走” | A 点位的站位坐标（从 `/waypoints` 查），`goals` 写 B |

所有坐标都是**地图坐标系**：单位米，原点为充电桩，x 轴为地图正前方，y 轴为 x 轴逆时针转 90°，角度为弧度。

## 第三步：发请求并保存结果

```bash
curl -s --noproxy '*' -X POST $A/plan -H 'Content-Type: application/json' \
     -d '{"start": {"x": 0, "y": 0, "yaw": 0}, "goals": ["厕所通道", {"x": 2, "y": 3}]}' > nav_plan.json

# 起点用仿真中的当前位姿
POSE=$(curl -s --noproxy '*' http://$H:8770/pose)
curl -s --noproxy '*' -X POST $A/plan -H 'Content-Type: application/json' \
     -d "{\"start\": $POSE, \"goals\": [\"广告牌\"]}" > nav_plan.json
```

- 把完整返回存成文件：仿真控制服务的 `POST /walk` 可以直接接收它，不要手抄折线。
- 中文目标名称直接写在 JSON 里即可（UTF-8）。
- 也可以用 GET：`$A/plan?x=0&y=0&goals=广告牌,厕所通道`，但 GET 只能写名称，不能写坐标目标。
- `step`（如 `0.2`）会在每段多给一份按间距加密的 `dense_path`，仿真行走用不着。

## 第四步：读懂返回

成功（`"ok": true`）时关心这些字段：

| 字段 | 含义 | 怎么用 |
|---|---|---|
| `map_id`、`map_version` | 规划所用的地图 | 与仿真服务核对 |
| `goals` | 每个目标最终匹配到的编号（坐标目标为 `"xy"`） | 核对是否理解对了用户的意思 |
| `total_length` | 全程长度（米） | 告诉用户；仿真中约 0.18 m/s，每段另加 5–10 秒 |
| `legs[i].goal` | 第 i 段目标：`id`、`name`、`stand_pose`（站位 x、y 和到达后朝向 yaw，坐标目标未给朝向时 yaw 为 null） | 告诉用户每段去哪里 |
| `legs[i].path` | 第 i 段折线 `[[x, y], ...]`：第一个点是该段起点，最后一个点是目标站位 | 交给行走控制 |
| `legs[i].length` | 第 i 段长度 | 汇报 |
| `warnings` | 提示，如“起点离障碍仅 0.20 m” | 原样转告用户 |

失败（`"ok": false`，HTTP 400）时：

| `error` | 处理 |
|---|---|
| 找不到名为「…」的点位 | 把返回中 `available` 列出的点位给用户，请用户选 |
| 「…」匹配到多个点位 | 换成完整名称或编号重发；拿不准就问用户 |
| 坐标目标 (x, y) 在障碍、未扫描区域或地图外 | 告诉用户这个坐标去不了，可以建议附近的点位 |
| 规划失败：目标不可达 | 起点多半不对（坐标来自别的地图、机器狗被推到墙外）；重新读位姿再试，仍失败就告诉用户 |
| 缺少起点 / 请求格式错误 | 修正请求后重发 |

**任何一个目标匹配失败，整个请求都不会规划**，修正后要整串重发。

## 向用户汇报

一两句话说清：起点、依次去哪些地方（名称 + 编号）、每段和全程多长、有无提示。例如：

> 从 (0.00, 0.00) 出发，先到 wp_02 厕所通道（4.6 m），再到坐标 (2.00, 3.00)（2.1 m），全程 6.7 m，无提示。
